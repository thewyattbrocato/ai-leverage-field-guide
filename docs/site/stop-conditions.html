Stop Conditions

Define "done" before you start. Observable. Falsifiable. Targets the real risk. Stop over-iterating, start shipping.

The Core Idea

A stop condition is a checklist, not a vibe.

You write it before you run the prompt. It has three criteria: Observable (someone else could verify it), Falsifiable (you can clearly fail it), Targets the Real Risk (not a proxy metric). If it doesn't meet all three, rewrite it.

Most people iterate until "it feels right." That passes everything and teaches nothing. A stop condition makes the finish line visible, testable, and tied to what actually goes wrong if you ship too early or too late.

The Three Criteria

1

Observable

Could someone else verify it without reading your mind?

Yes: Every factual claim has a source. Every number traces to a document. The ask is explicit in the first two lines. Unverified claims are flagged.

No: "Looks good to me." "Feels right." "Professional tone."

2

Falsifiable

Can you clearly FAIL it? (Not "good tone" — that passes everything.)

Yes: "Every number traces to a source document." "The requested action appears in the first two lines." "All requested sections are present."

No: "Until I'm confident." "High quality." "Make it better."

3

Targets the Real Risk

Not a proxy. What actually goes wrong if you stop too early or too late?

Yes: "Missing the explicit ask causes my manager to forward a vague email." "An untraced number triggers a compliance review." "An unverified claim damages credibility with the client."

No: "Word count." "Readability score." "Number of revisions."

Decision Sequence

Before you run the prompt, write your stop condition. Then check it against these three questions:

Q1: Is it Observable?

Could a colleague verify it without asking you? If NO → REWRITE: Make it observable

Q2: Is it Falsifiable?

Can you clearly fail it? If NO → REWRITE: Add a fail condition

Q3: Does It Target the Real Risk?

What actually goes wrong if this passes but the work is bad? If NO → REWRITE: Find the real risk

ALL YES → STOP CONDITION READY

Observable | Falsifiable | Targets real risk — Ship when it passes.

Starter Template

A blank stop condition to adapt by hand or paste into your notes:

# Stop condition — [work type]

## Intended outcome
[What should exist when this work is done]

## Evidence required (observable)
- [Check someone else could verify]
- [Check someone else could verify]

## Clear failure condition (falsifiable)
This FAILS if:
- [Condition that clearly fails the work]

## Real risk
What actually goes wrong if this ships bad:
- [Consequence, not a proxy metric]

Good Examples

These pass all three criteria:

  • Every factual claim has a source
  • Every number traces to a source document
  • The requested action appears within the first two lines
  • Unverified claims are explicitly flagged
  • All requested sections are present
  • Nothing missing that was in the original request

Bad Examples (and Why They Fail)

"Until it feels right"

Fails: Observable, Falsifiable, Real Risk. No one else can verify your feelings. You can't fail "feels right." It targets confidence, not risk.

"Until I am confident"

Fails: Observable, Falsifiable, Real Risk. Confidence is internal. It passes everything. It doesn't catch the actual failure mode.

"Good tone"

Fails: Observable, Falsifiable. Tone is subjective. Everything passes "good tone." It's a proxy for voice, not a measure of risk.

"High quality"

Fails: Observable, Falsifiable, Real Risk. Undefined. Passes everything. Quality of what? For whom? At what cost?

"Make it better"

Fails: Observable, Falsifiable. Infinite loop. No defined end state. Better than what? By whose standard?

"Professional standard"

Fails: Observable, Falsifiable. Whose standard? Which profession? A proxy that sounds rigorous but means nothing specific.

Examples by Work Type

Status Update

  • Numbers traced to tickets
  • Ask explicit in first 2 lines
  • Blocked items truly blocked
  • No jargon, under 200 words

Email / Follow-up

  • One clear ask
  • Actionable by recipient
  • Context sufficient for reply
  • Deadline or next step stated

Brief / Strategy

  • Claims sourced
  • Max 2 unverified, flagged
  • Diagnosis → Policy → Action clear
  • Risks named, not hidden

Summary

  • Nothing missing from source
  • Nothing added not in source
  • Key decision + rationale included
  • Next actions explicit

Creative Work

  • Time-box: 3 passes, then decide
  • Specific criteria per pass
  • Version saved at each pass
  • Final choice documented

Rewrite Exercise

Practice: Fix These Stop Conditions

For each weak example, write a version that passes all three criteria.

Weak Stop Condition Fixed (Observable + Falsifiable + Real Risk)
"Until the tone is professional" "No hedging words (just, perhaps, maybe). Direct requests in imperative mood. Recipient can act without clarification."
"Until I'm happy with it" "All 3 sections from the template present. Every number traces to source. Ask explicit in line 1. Zero unverified claims."
"High quality output" "Passes the stop-condition checklist for this work type. Peer reviewer would sign off without edits."
"Good enough to send" "Meets the specific stop condition written for this task type before the prompt ran."

Final Checklist

Before you run any prompt, complete this:

  • I have written a stop condition for this task
  • It is observable (someone else could verify)
  • It is falsifiable (I can clearly fail it)
  • It targets the real risk (not a proxy)
  • I will check the output against it like a checklist, not a vibe

Write the stop condition FIRST. Then run the prompt. Check like a checklist, not a vibe.
